## 2. Did the useCloneStamp split pay off?

**Yes locally, no globally.**

The split is durable. `useCloneStamp.ts` is 229 lines and has stayed there
through ten releases — no re-accretion, which is the thing that usually undoes
a decomposition.

What did not happen is a reduction in clone families. They moved:

```
89 lines  3 instances   useMagicEraserTool.ts · useMoveLayerTool.ts · usePaintTool.ts
60 lines  2 instances   useEngineCore.ts · lib/exportImage.ts
        3 groups, 70 lines entirely INSIDE useEngineCore.ts
```

`useEngineCore` is now 797 LOC, a `risk` file, and the site of five clone
groups (three internal, two shared with `exportImage`). The five domain hooks
that came out of the split share an 89-line triplicate across
`useMagicEraserTool` / `useMoveLayerTool` / `usePaintTool` — the same
"acquire the engine, guard, flush" shape written three times.

So: the split moved a 1,467-line hook into a set of files whose *individual*
sizes are healthier and whose *shared* code was never extracted. Total
duplication is unchanged at 4.0%.

## What this suggests, without doing any of it

1. **CanvasArea now deserves the treatment AppShell is getting**, and is
   probably the better next target: 2,102 lines in one function, accelerating,
   and not yet load-bearing for a half-finished plan.
2. **The 89-line triplicate across the three tool hooks** is the cheapest real
   duplication win — one extraction, three call sites, all in files that were
   already touched by the clone-stamp split.
3. **Extraction rate vs accretion rate in AppShell** is the number to watch. It
   grew 94 lines across ten releases *while being actively dismantled*. If the
   next report shows the same, the plan needs a different shape, not more
   patience.
4. **Teach `.fallow` about the union tuples** so the top refactoring target
   stops being a false positive that someone eventually acts on.
