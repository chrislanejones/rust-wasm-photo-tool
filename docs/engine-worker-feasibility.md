# Engine-in-a-worker — Phase 0 feasibility

**Night of 2026-07-27.** Research and measurement only. No migration, no
call-site changes, nothing merged but this document and a throwaway spike on
`spike/engine-worker`.

Everything below is measured unless it says otherwise. Where something could
not be settled it is logged as **OPEN** rather than guessed.

---

## The four questions, answered

| Question | Answer |
| --- | --- |
| Does this need `SharedArrayBuffer`? | **No.** Not for a transfer-based worker. |
| How many call sites change, and of what kind? | **206 total** — 77 fire-and-forget, **117 value-consumed (the hard ones)**, 12 hot-path. |
| What does a worker round-trip actually cost? | **0.100 ms** median fixed (p95 0.300 ms) — **0.6% of one 60fps frame**. |
| Can the main canvas be transferred? | **Very likely yes.** It has exactly one writer. |

**Headline: latency is not the obstacle. The obstacle is 117 synchronous reads.**

## Phase 1 — cross-origin isolation

### What is true today

- `netlify.toml` sets **no** COOP/COEP headers. Confirmed by reading it: there
  is no `[[headers]]` block for cross-origin policy at all.
- The live site is **not** cross-origin isolated. Measured on
  `rust-wasm-photo-tool.netlify.app`: `crossOriginIsolated === false`,
  `typeof SharedArrayBuffer === "undefined"`.
- **The rayon-parallel blur is NOT threaded in the shipped binary.** `threads`
  is an optional Cargo feature (`threads = ["dep:wasm-bindgen-rayon", "dep:rayon"]`)
  and the shipped build passes `--features tiles,patchmatch` — in both
  `package.json` and `netlify.toml`. It is compiled to scalar. (Consistent with
  the rayon NNF result, which was rejected for being 8–31× slower.)

So the app ships zero threads and zero `SharedArrayBuffer` today.

### Therefore

A worker that owns its own wasm instance and exchanges **transferable**
`ArrayBuffer`s needs no shared memory, and so needs no COOP/COEP. The isolation
question only returns if someone later wants wasm *threads* inside the worker —
which this project has already tried and rejected once.

### It would work anyway, if it were ever needed

Served the production build locally with `COOP: same-origin` +
`COEP: require-corp` (`spike/coep-server.mjs`, port 5402):

| Subject | Result |
| --- | --- |
| `crossOriginIsolated` | **true** |
| `SharedArrayBuffer` | **available** |
| Clerk SDK load + reach its frontend API | **WORKS** |
| wasm engine boot | **WORKS** |
| Console errors / CORP-blocked assets | **none** (only the pre-existing "development keys" warning) |

**"Clerk breaks under COEP" is NOT the finding.** Clerk's SDK loads fine under
require-corp.

**OPEN-A — the untested half.** Clerk *loading* is not Clerk *signing in*. The
hazard with `COOP: same-origin` is specifically OAuth popup flows: it severs
`window.opener`, which is how popup-based sign-in returns its result. This was
not exercised — the COEP preview runs on a different origin, so no session
cookie was present, and driving a real OAuth sign-in needs credentials. If
threads are ever pursued, test social sign-in specifically, not just page load.
Convex websocket, Stripe checkout and Replicate calls were likewise not
exercised for the same reason, though none of their assets were CORP-blocked at
page load.

## Phase 2 — the sync→async audit

**This is the size of the job.** Generated by `scripts/engine-call-audit.mjs`,
which takes the method list from the engine's own `stamp_tool.d.ts` (231
declared members) rather than a hand-written list, so a new engine method cannot
silently escape the count.

### Totals

| Category | Count | What it costs in a migration |
| --- | ---: | --- |
| **(a) fire-and-forget** | **77** | Cheap. Return value unused; a `postMessage` is enough. |
| **(b) value-consumed synchronously** | **117** | **The hard ones.** Each needs a Promise *and* a call-site restructure. |
| **(c) per-frame hot path** | **12** | Round-trip latency (answered below: not a problem). |
| **Total** | **206** | across 32 files |

> **Accuracy note.** A first pass reported 306 by also matching a bare `t.`
> handle, which swept in ~100 `rect.width`/`t.height` hits on unrelated objects.
> 206 is the figure after removing it. Believe 206.

### By owning file (a / b / c)

| File | a | b | c | total |
| --- | ---: | ---: | ---: | ---: |
| `hooks/useEngineCore.ts` | 30 | 16 | 0 | 46 |
| `hooks/useTransforms.ts` | 18 | 7 | 0 | 25 |
| `app/AppShell.tsx` | 8 | 15 | 0 | 23 |
| `app/session/useSelectionActions.ts` | 4 | 18 | 0 | 22 |
| `hooks/useDrawingTools.ts` | 5 | 6 | 7 | 18 |
| `lib/editPersistence.ts` | 0 | 18 | 0 | 18 |
| `hooks/useTextTool.ts` | 7 | 10 | 0 | 17 |
| `lib/openraster/export.ts` | 3 | 14 | 0 | 17 |
| `app/session/useCanvasActions.ts` | 3 | 11 | 0 | 14 |
| `features/tools/settings/BatchSettings.tsx` | 7 | 7 | 0 | 14 |
| `hooks/useEditPersistence.ts` | 2 | 12 | 0 | 14 |
| `hooks/useLayers.ts` | 1 | 13 | 0 | 14 |
| *(20 more files)* | | | | ≤10 each |

Two observations worth carrying into the design:

- **`useEngineCore` is mostly fire-and-forget (30 of 46).** The file the brief
  forbids touching is, encouragingly, the *least* affected by async.
- **The pain is concentrated in four places** — `useSelectionActions` (18 b),
  `editPersistence` (18 b), `openraster/export` (14 b), `useLayers` (13 b).
  Those four hold 63 of the 117. They are batch/serialisation paths, not
  interaction paths, which is the good case: they can `await` freely.

### The most-repeated synchronous reads

`width` (7), `height` (7), `export_png` (7), `get_shape_annotations` (6),
`get_text_annotations` (6), `layer_count` (5), `get_image_data` (3),
`get_image_data_excluding_background` (3), `active_layer_id` (3),
`lasso_active` (3).

`width`/`height`/`layer_count`/`active_layer_id` are cheap scalars read
constantly. **A mirrored state snapshot pushed from the worker on every change
would erase roughly 25 of the 117 without any call site becoming async** —
they'd read a plain local object. That is the single highest-leverage idea this
audit produced.

### The 12 hot-path sites

```
CanvasArea.tsx:688        selection_preview
CanvasArea.tsx:2018       measure_text
CanvasArea.tsx:2185       text_ink_offset
useCloneStamp.ts:137,152  end_stroke
useDrawingTools.ts:303    set_editing_shape
useDrawingTools.ts:308    update_shape_annotation
useDrawingTools.ts:364    set_editing_shape
useDrawingTools.ts:427    set_editing_shape
useDrawingTools.ts:484    get_shape_annotations
useDrawingTools.ts:653    shape_annotation_at
useDrawingTools.ts:771    crop
```

Most are *fire-and-forget* even here (`set_editing_shape`, `update_shape_annotation`).
The genuinely awkward ones are `measure_text` and `text_ink_offset` in
`CanvasArea` — they are called **during render** to lay text out. An async read
cannot be awaited inside a render pass; those two need either the mirrored
snapshot above or a layout cache, not a Promise.

## Phase 3 — the spike, and the number

Standalone page (`spike/index.html` + `spike/engine.worker.js`), not wired into
the app. A 4000×3000 photo (48 MB RGBA), `adjust_sharpen` as the cold-path
operation, 5 runs, medians.

| Measurement | Result |
| --- | ---: |
| **Fixed round-trip, empty payload** (50 pings) | **0.100 ms** median, **0.300 ms** p95 |
| — as a share of one 60fps frame (16.7 ms) | **0.6%** |
| Cold op, synchronous on the main thread | 468.6 ms |
| Cold op, via worker round-trip | 483.6 ms (**1.03×**) |
| Messaging overhead carrying a 48 MB transferable | **0.5 ms** |
| One-off: wasm `init()` inside the worker | 8.5 ms |
| One-off: 48 MB transfer into the worker | 67.5 ms |

**The boundary is effectively free.** Transferables move a pointer, not 48 MB,
so payload size barely registers; 0.5 ms of overhead sits inside the run-to-run
noise of the operation itself. Even a per-frame call would spend 0.6% of its
frame budget on the round trip.

Two honest caveats:

1. **0.1 ms is the messaging cost, not the async cost.** The real expense of
   async is structural: the value arrives on a *later task*. Anything reading
   engine state during a render or synchronously inside a pointer handler must
   be restructured, not merely `await`ed. That is the 117, and no latency
   measurement makes it smaller.
2. The spike carries no request-id demultiplexing, queueing, cancellation or
   error protocol. A real implementation adds all four. They cost complexity,
   not milliseconds.

Prior art worth noting: **the codebase already runs a worker** —
`app/src/workers/codec.worker.ts`. The pattern is not new here.

## Phase 4 — OffscreenCanvas reconnaissance

**The main canvas has exactly one writer.** That is the finding, and it is a
much better position than expected.

| Component | Touches the main canvas how? | Survives transfer? |
| --- | --- | --- |
| `useEngineCore` | **The only writer.** 4 × `getContext("2d", {desynchronized:true})`, plus `canvas.width/height` assignments | Must **move into the worker** |
| `CanvasArea` | `getBoundingClientRect()` **once** — measures, never draws | **Yes** — layout reads are unaffected |
| `SelectionOverlay` | Its own canvas, sized to match the main one | **Yes** |
| `HistogramView` | Its own canvas | **Yes** |
| `CompareSlider` | Positions/measures only | **Yes** |
| `LassoOverlay`, `PenOverlay` | SVG overlays | **Yes** |
| Guides / marquee / magnifier | SVG or CSS-positioned | **Yes** |

Constraints found:

- After `transferControlToOffscreen()`, the main thread can never again get a
  context from that element **and cannot set `canvas.width` / `canvas.height`** —
  those assignments (useEngineCore ~lines 240, 324, 406) must move into the
  worker as messages. This is the concrete work item, not a blocker.
- `desynchronized: true` is already in use on every main-canvas context, which
  suggests latency was already being tuned there; worth confirming OffscreenCanvas
  keeps that behaviour.
- `OffscreenCanvas` is **already used** in `useEngineCore` (a decode helper), so
  the API is available and understood in this codebase.

**OPEN-B.** Whether the overlays' *visual* alignment survives is argued from
structure, not observed — none of them were changed or run against a transferred
canvas. Zoom/pan currently work by CSS-sizing the canvas element while its
backing store stays at image resolution; that split needs confirming under
transfer before anyone commits.

## What this does NOT decide

Per the brief, no option is chosen here. See `docs/adr/024-engine-in-a-worker.md`
for the options and the pre-mortem.

**OPEN-C — the sequencing question, raised because it was invited.** #1's safety
net is still missing: the registry↔routes↔palette↔ShortcutModal↔dispatch
contract test, ADR-023, and QC against v7.51–56. Tonight's work *opens* an arc
rather than closing one. Having now measured #2, the case for closing #1 first
is stronger than it looked: the 117 rewrites will touch dispatch and tool state,
and doing that without the drift guard in place is how the toolbar arc's
mislabelling bugs happened. The contract test is worth more before this
migration than after it.
